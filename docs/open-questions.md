# Remaining work after planning completion

Reconciled **17 October 2026** against D01–D251 in the [decision register](decisions.md). **Product and architectural planning for the agreed minimum viable product (MVP) is complete.** Account-owned contacts with logbook tags, one synchronization scope per account and unique external-record associations are part of the current [product model](product.md#contacts-logbooks-and-tags), not a separate proposal. [Architectural review](architecture-review.md) findings AR1–AR4 are resolved at the design/documentation level; implementation verification remains. The stale synchronization-scope and process-topology wording identified in the follow-up review has been corrected under existing decisions.

This file retains its existing path as an index of remaining engineering work and deferred matters. Entries below are not a product-decision backlog or an approval queue. Concrete schemas, protocol messages, transaction handling, mappings, dependency configuration, data preparation and validation are implementation specification/design or verification work. Their incompleteness does not mean product planning remains open.

No application implementation, prototype, implementation-plan execution, migration or publication is authorized by this completion checkpoint. A demonstrated contradiction, missing requirement or material behavioral/architectural tradeoff can justify a focused decision later; ordinary engineering details do not.

## Implementation specification and validation

The following work realizes the selected architecture and accepted behavior. It is not a list of unresolved product or architectural choices.

### Client and server engineering

#### Synchronization protocol and recovery

The [replication survey](../references/replication-research/approaches-survey.md), [recommended combination](../references/replication-research/recommended-model.md) and [recovery-fit analysis](../references/replication-research/recovery-fit.md) supply conceptual research. They are not an implemented protocol or a proof of every Clacks-specific recovery case. Remaining work is to specify and validate the selected combination:

- Represent vector knowledge, timeline ancestry/coverage, record positions, actor retirement and explicit reauthorization under D151–D155. Revocation closes automatic acceptance from the old actor; recovered unsynchronized work requires manual reconciliation. Do not require lost-device cooperation or expire unrevoked clients because of inactivity.
- Define account-scope initialization and tag/reference validation under D248. All account QSOs, tags and synchronized shared data reach every enrolled client in MVP. Tag deletion uses D244’s preserve/mark-deleted choices. D250 requires pending QSOs with deleted-tag references to remain local until explicit membership removal/replacement; unrelated synchronization continues. Specify atomic reference revalidation under these selected semantics.
- Specify common covered ancestry, installed compaction baselines, surviving-reference interpretation and fuller-state fallback. D155 retains detailed ordering evidence from the oldest authorized client's durably acknowledged point; D156 requires atomic local installation before acknowledgment. Deletion and service-processing evidence have separate retention obligations. Validate rollback below retained baselines and interrupted baseline installation.
- Specify atomic conditional acceptance, retry identity, responses, gap-free batch catch-up/stream handoff, acknowledgments, backpressure and transport. D235 selects encrypted WebSocket sessions following the [transport comparison](../references/synchronization-transport.md); exact message and flow-control mechanics remain specification work. Use standard mechanisms; do not infer permanent history for every edit, a storage quorum, a per-record ancestry graph or a new actor on ordinary restart.
- Implement the accepted whole-record three-way trigger and field-level resolution: equal/one-sided results need no flow; differing both-sided results do. Define equality and reference validation. Preserve local originals/pending work; D147/D148 supply explained recovery fallbacks when original values or ordering evidence are unavailable. Broader interdependent-field conflict modeling is post-MVP.
- Specify initial empty-log enrollment, recovery of retained state after reauthorization, reconciliation using surviving rollback evidence and D179 compatibility negotiation/migrations. Preserve enrollment, pending edits and comparison evidence through required upgrades. Do not promise survival of facts absent from every available copy, including later revocations lost by server rollback.
