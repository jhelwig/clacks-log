## Selected architecture

- **Desktop:** Rust with egui/eframe and egui_extras (D215); Windows MVP, macOS/Linux releases later, with cross-platform architecture/tooling from the start (D162). No system-tray requirement. Embedded SQLite (D213), ordinary database-library transactions and contention handling, no prescribed custom write queue. Ordinary Serde serialization (D216).
- **Server:** one Clacks application containing web, synchronization and background workers, plus PostgreSQL (D213). Linux-container deployment (D189). Independently deployed application services sharing tables are not the topology. Full production-grade tracing, structured logs and metrics, including operator security events without secrets, are MVP requirements (D230).
- **Web:** Leptos/Axum with server rendering and Rust/WebAssembly hydration (D223). MVP covers administration/setup/diagnostics; architecture accommodates future logbook browsing/editing, reporting and potentially logging (D222), without adding those to MVP or promising browser offline synchronization.
- **Identity:** configurable OpenID Connect (OIDC), with deployment-configurable provider selection. Stable internal accounts have multiple external issuer/subject login bindings; each external identity maps to at most one account (D231). First-sign-in provisioning, out-of-band administrator assignment, browser-callback desktop enrollment, individual-client revocation and multi-account isolation are selected. MVP includes safeguarded self-service identity linking/unlinking (D232); administrator-assisted exceptional recovery is sufficient (D233).
- **Secrets:** independent account encryption keys protected by a deployment wrapping key outside PostgreSQL and the application image (D236). Store wrapped account keys and encrypted credentials in PostgreSQL; document key/database recovery together. Client secrets use protected local storage; ordinary log data requires no application unlock/encryption workflow. LoTW signing keys remain server-side.
- **LoTW:** source-guided Rust port, not a direct TrustedQSL foreign-function interface or black-box reverse engineering. D224 selects established pure-Rust certificate import/interpretation/signing and rejects OpenSSL as the backend. The [cryptographic comparison](../references/lotw-cryptography.md) supplies an engineering starting composition; exact versions/features and interoperability/security verification remain work, not another backend-policy question.
- **Geography:** Census for United States (US) states/counties, HA8TKS for CQ/International Telecommunication Union (ITU) zones, Natural Earth with an explicit DX Century Club (DXCC) mapping/exception layer (D239). The [comparison](../references/location-lookup.md) and [audit](../references/geographic-data-audit.json) record terms, provenance and limitations. Compiling mappings, correcting topology and validating artifacts remain data engineering; selection does not claim a completed global dataset.

## Synchronization contract already selected

Any number of enrolled clients remain independently writable offline, with indefinite authorized offline return. Dynamic version-vector causal tracking and exceptional timeline ancestry are selected; ordinary restarts do not create actors/timelines, and no per-record revision-history graph or storage quorum is required (D151–D154). Actor estimates are workload estimates, not caps: 20 active actors would be exceptionally high; 100+ lifetime actors extremely rare and lifetime total almost certainly below 1,000.

One synchronization scope and timeline per account covers QSOs with tag sets, tag definitions, service evidence and synchronized shared configuration (D248). Preserve vector/timeline recovery, durable acknowledgments, indefinite authorized offline operation and retention through the oldest authorized client. Conflict granularity remains per record; bounded acceptance batches remain possible. D161 full-account replication to every client remains. Current tag selection does not affect replication or server jobs.

Whole-record three-way comparison skips resolution for equal results or one-sided changes. Differing results changed on both sides require client-side field resolution, including disjoint-field edits (D136/D137). Pending proposals remain local; there is no server conflict queue or silent last-writer-wins policy. Conditional acceptance must revalidate shared state atomically (D146). Tag membership is part of the QSO record, so concurrent tag/fact or different-tag changes can require resolution (D243). Deletion is a comparison state. Tag deletion applies explicit leave-all/delete-all/delete-unique QSO choices (D244); pending QSOs with deleted-tag references stay local until explicit membership removal/replacement (D250).

Retain ordering evidence from the oldest authorized client's durably acknowledged point, with equivalent baselines and required surviving references (D155). Install received state, pending comparison evidence and checkpoints durably before acknowledgment (D156). Unresolved work does not block unrelated sync. Fuller-state fallback and explained conservative/manual recovery are accepted when history, originals or ordering evidence are unavailable. Revocation closes automatic acceptance from that actor; recovered unsynchronized work requires manual reconciliation, while already accepted data stays recoverable (D145/D152).

Encrypted WebSockets carry bounded catch-up and ongoing bidirectional updates in the existing server (D235). Exact messages, encoding, retry identity, flow control, transfer boundaries and compaction mechanics are engineering specification/validation. They are not unresolved product decisions.

For rollback/restore, the operator pauses uploads, uses normal sync to recover as current a state as available sources allow, then explicitly resumes (D141). Client conflicts do not give a server-publication veto. Later revocations or other facts lost from all restored/surviving copies cannot be promised to survive rollback. Diagnostics are connection state, last successful sync and current error (D142). See the [replication research](../references/replication-research/README.md) and [selected model/recovery analysis](../references/replication-research/recovery-fit.md); do not restart software-fit research or reinvent causal schemes.

## Product and integration guardrails

Radio contacts (QSOs) capture station context at logging time; later defaults/profiles do not rewrite them. Current operating defaults and operator identity are client-local. Saved profiles and reusable equipment synchronize; profile reload is explicit. QSOs are account-owned and carry zero or more logbook tags. Tag definitions support offline creation/rename/deletion and duplicate names with distinct identities. The open tag supplies default membership for new contacts and filters history/Worked Before. Add/remove tags on individual contacts or selected groups in MVP; removing the last tag leaves an active, accessible untagged contact. Deleting a QSO marks the contact itself deleted across normal views, distinct from removing memberships. Automatic source/reference/date assignment and tag creation remain outside MVP. Local working state appears once per QSO with pending/conflict markers; pending deletions are hidden from normal views but available in account-wide review.

LoTW and QRZ jobs run server-side. Each tag defaults to Neither independently per service; any Forbid wins over Enable, otherwise at least one Enable grants automatic-upload eligibility. All-Neither/untagged QSOs have no grant. Manual-upload policy remains unchanged. Each new attempt uses current accepted effective output; retry unless explicitly successful, with detailed diagnostics and affected-only pauses for clearly non-transient failures until remedy/resume. Imported positive upload/confirmation statuses are accepted immediately with provenance; missing upload status is pending. Multiple certificates/QRZ logbooks route by saved station callsign/date; missing or ambiguous routing pauses affected uploads. Supersession is explicit, with coverage-gap preview. Credential removal preserves public metadata/submission history. Local deletions leave external copies untouched and suppress later re-add offers.

D237/D238 supersede automatic replacement of recorded facts by confirmation enrichment. Keep provider information separate. Logical fallback is **recorded QSO → eligible LoTW → eligible QRZ → eligible directory snapshot**. Select location as a whole, never patching from lower-priority sources or changing recorded facts. Apply consistently to display and supported exports/uploads, retaining provenance and existing applicability rules. Directory snapshots use latest-successful-lookup arbitration with deterministic ties, not user conflict resolution. Same normalized callsign key retains its snapshot; key changes immediately stop old-snapshot use. QRZ/HamQTH directory lookup is client-direct, using the account-selected provider only; no merging, automatic fallback or reconnect-triggered bulk lookup. Bulk lookup is user-triggered, applies results as they arrive, and reports partial failures.

One capturing client per WS Suite (the WSJT-X family of weak-signal radio applications) source, other clients receive QSOs through sync. Incoming other-station (DX) calls are authoritative including empty values; use 500 ms lookup debounce and clear associated displays on empty calls. No outbound WS call control in MVP. Manual start/end fields independently live-update until locked and both reset to live after saving. There is no separate live/historical manual-entry mode or restart-persistent unsaved draft requirement.

Amateur Data Interchange Format (ADIF) is interchange, not a lossless native backup/model. MVP uses the ADIF text format (ADI); the ADIF Extensible Markup Language (XML) format (ADX) is later. Imports prepare/map/validate before changes, show unsupported fields and structural errors, allow reliably decoded prefixes/partial results, skip confident unchanged matches, and retain completed changes on cancellation/crash. Normal re-import handles recovery; no import-session resumption or opaque unknown-field retention. Imports match account-wide and add the chosen tag to reused contacts. Update changes the shared QSO and adds the tag; Duplicate creates a separate contact; Skip changes neither facts nor tags. Report membership additions separately from unchanged facts. Possible matches require explicit selection even when unique, with a 30-minute window alongside stricter confident rules; downloads search account-wide, with at most one local QSO associated with each external record per account/service destination under D251. Ambiguous external matching selects at most one QSO; outgoing collisions with an occupied association require resolution rather than silent replacement. Rejected unmatched versions suppress identical repeats, not changed versions. Exports use consistent saved local working state including unsynced/conflicted values, exclude pending deletions and preserve existing destination files on failure/cancellation. Optional Parks on the Air (POTA)-compatible expansion is separate from ordinary one-entry-per-QSO export. Native mode uses a hierarchical enum with structured unknown fallback; interpretation changes must not create edits/conflicts.
