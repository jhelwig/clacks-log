# Unified Desktop Settings Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Steps use checkboxes for tracking.

**Goal** — Deliver one desktop Settings editor for [Clacks Log #48][issue], with one draft, independent outcomes from one Apply, and automatic sync pause and resume.

**Architecture** — The main window owns navigation, draft forms, previews, and feedback. The desktop session owns synchronization, workspace readiness, and settings reads and writes. Preserve the existing store transaction for each domain operation, the receiver's save and activation outcomes, and the appearance preference store.

**Tech stack** — Rust 1.99.1, egui/eframe 0.37.0, muda, Tokio, and the SQLx SQLite client store.

**Spec** — [Unified desktop Settings design][design].

## Global constraints

- Use the existing native menu adapters on Windows and macOS and the egui fallback on Linux. Follow the [desktop UI contract][ui] for controls, theme, and acceptance.
- Keep the unfinished contact, direct access to sync status and conflict review, active Operating settings, and its nested reusable-record saves in the workbench workflow.
- Apply processes all independent changes, clears its submitted draft on completion, and shows saved values plus local diagnostics. Connect and Reauthorize retain their existing browser workflow.
- Keep the current account and workspace ownership, stale-write protection, durable sync receipts, and domain transaction boundaries. The plan uses the existing model, schema, and wire protocol.
- Before execution, use the assigned isolated worktree and carry the reviewed spec and plan into it. Use temporary workspaces for automated tests. Read the machine-local development inventory before any development launch. Explicitly pass isolated workspace, configuration, and log-directory paths for native smoke checks.
- Verify each logical change at its owning boundary. When committing execution work, inspect the actual message, hard-wrap its prose at 72 columns, and use `git commit --file`.

## Review focus

| Case | Owning check |
| --- | --- |
| Settings opens as an inbound page or pending proposal settles, or closes during workspace reopen. | Task 1 exercises the pause boundary and the latest screen intent across lifecycle transitions. |
| A write commits, its refresh fails, and the operator has already started another edit when recovery completes. | Tasks 2 and 4 check authoritative outcomes, one write, and retained newer input. |
| A draft creates equipment and refers to it from a profile, then one of those writes fails. | Task 3 checks operation order and the existing missing-reference behavior. |
| Two reviewed deletions touch the same contact, or a staged profile edit changes an equipment deletion's impact. | Task 3 checks projected effects and exact revalidation. |
| Apply saves a receiver preference but socket activation fails, or rejects one setting while saving others. | Task 4 checks saved values, local diagnostics, and the cleared draft. |

## Task 1 — Pause and resume the workspace sync driver

**Files** — `application.rs`, `session.rs`, `synchronization.rs`, `synchronization/exchange.rs`, `session/tests.rs`, and `enrollment/tests/synchronization.rs` in `lib/clacks-desktop/src/`.

**Interface** — Use `watch::Sender<Option<SettingsSessionId>>` for the UI's current open intent, with a new ID each time it opens. A latest-value channel preserves close intent when the session is busy. Return readiness through `watch::Receiver<Option<SettingsBasis>>`, where `SettingsBasis` carries the Settings session ID, current workspace identity, and fresh `Arc<SettingsSnapshot>`. Clear readiness when the open interval or workspace changes and accept only a basis matching both. Appearance can open independently of workspace readiness.

- [ ] **Pin the lifecycle at the production session boundary.** Extend the existing enrolled two-client fixture with `settings_pause_defers_incoming_and_outgoing_until_close`. Synchronize a shared record first. Open Settings with an exchange in progress, wait for readiness, then save a different local record and change the shared record on the other client. Assert that the first client sees neither the incoming change nor publication of its new local edit until closing Settings. After close, assert both changes converge through the ordinary driver. Use the existing fixture's protocol or store observation points for barriers, rather than sleep-based absence checks.
- [ ] **Pin admission during transitions.** Extend the session and enrollment completion tests to exercise close during pause, opening while startup is in flight, Connect-driven reopen with Settings still open, and shutdown during pause. Assert that only a ready, enrolled workspace with no Settings pause and no shutdown can start a driver. Verify that a competing edit to the same record is handled after resume by the existing reconciliation path.
- [ ] **Use the existing stop-and-join lifecycle.** Observe the latest open intent before driver admission. Cancel the current sync token and use the existing join branch to observe settlement. Let an entered local store operation finish. The existing send/receive cancellation and transfer checkpoint rules make interrupted exchanges repeatable. Preserve the driver join through directory provisioning cleanup. Check the authorization/connect and reconnect-delay paths so opening Settings during a network wait can settle. Never abort an in-flight store task or acknowledge readiness before its driver has exited.
- [ ] **Publish the editing basis and honor the latest open intent.** After sync and already admitted settings mutations settle, read a fresh settings snapshot before enabling workspace edits. Gate the existing `start_sync` call and the close-driven restart in the session on current workspace, enrollment, Settings intent, and shutdown. Resume with a fresh cancellation token and the existing driver entry point, once the old task is joined and enrollment or reopen has settled. Keep the open intent in the session across workspace reopen. Preserve committed receipts, pending proposals, and cancellation-safe local changes across the boundary.
- [ ] **Verify the lifecycle.** Run the focused session and enrolled-sync tests with `cargo +1.99.1 test -p clacks-desktop --lib --locked --offline settings_pause`. Run existing enrollment and sync regressions for the touched paths. Success means no premature readiness or publication, exactly one resumed driver, and normal post-resume convergence.

## Task 2 — Recover the settings view automatically

**Files** — `session.rs`, `session/settings.rs`, `session/tests/settings.rs`, and the workbench files in the file map.

**Interface** — Keep `settings::Completion` and `SettingsResponse::RefreshFailed { outcome, message }` as the distinction between authoritative operation results and unavailable views. Keep the settings snapshot watch as the publication path. If a caller detects a lost response, send `SessionCommand::RecoverSettingsView` to the owning session with the same automatic reread behavior.

- [ ] **Pin confirmed and uncertain results.** Exercise a committed profile or logbook operation with the next settings read forced to fail at the read boundary. Assert that the response retains the successful operation and that a subsequent read publishes its result without sending another write. Exercise an interrupted power response and assert that recovery reads back the applied power before the workbench can report a confirmed value. Reuse the session fixture and real SQLite operations; inject only the otherwise hard-to-reproduce boundary failure.
- [ ] **Schedule rereads in the existing session.** On a failed follow-up read, or a write response whose completion was lost, schedule the existing settings snapshot read with a delay through the session runtime. Coalesce repeated requests per open workspace, reschedule transient read failures with capped backoff, and cancel or discard results on shutdown or workspace replacement. Suppress a recovered snapshot superseded by a newer publication. Keep the last verified view and confirmed per-operation outcomes while reads are failing. Use the returned state to verify what value is stored. Where the read cannot prove the outcome of an operation, keep that outcome unverified and avoid automatic mutation replay.
- [ ] **Wire recovery to its callers.** Replace workbench messages that instruct the user to refresh with outcome-specific feedback. Remove the workbench **Refresh logbooks** recovery control. Replace the menu command in Task 4. For an opening Settings basis, use the same recovery path on read failure and enable workspace editing only with a fresh result for that pause interval.
- [ ] **Verify recovery.** Run `cargo +1.99.1 test -p clacks-desktop --lib --locked --offline session::tests::settings` and the affected logbook and operating UI tests. Confirm successful deletion or selected-view fallback stays visible if its follow-up read fails.

## Task 3 — Sequence staged account changes through guarded store operations

**Files** — `session/settings.rs`, new `session/settings/apply.rs`, `session/settings/logbooks.rs`, `session/tests/settings.rs`, and the existing client-store preview and mutation modules named in the file map.

**Interface** — Add `SettingsAction::ApplyAccountChanges(AccountChanges)` and `SettingsResponse::ApplyAccountChanges(AccountApplyResult)`. Define both payloads in `session/settings/apply.rs`. `AccountChanges` carries typed edits keyed by existing record identities, original bases for persisted records, and the reviewed inputs for each planned deletion. `AccountApplyResult` identifies each attempted operation and its saved, unchanged, rejected, or unverified result, with authoritative returned records or deletion effects where available. The screen retains raw input and inline validation.

- [ ] **Pin draft dependencies and reviewed effects.** Add `settings_apply_orders_staged_equipment_and_profiles` using a temporary real store. Check that a new profile can reference equipment created by the same Apply, and that prerequisite failure follows the existing profile missing-reference rule while a separate logbook rename still saves. Add `settings_apply_revalidates_overlapping_deletion_reviews`. Stage two logbook deletions that affect a shared QSO, and exercise an equipment deletion with a staged change to a referring profile or replacement. Assert the committed effects match the reviewed impact. Change a reviewed record at the same count and assert the affected deletion commits no effects, while an independent write still succeeds.
- [ ] **Reuse guarded write calls.** Execute the account changes as a single request on the existing serialized settings worker, with the existing store methods for tag, equipment, and profile writes. Assign new records their existing typed IDs at form creation. Apply equipment upserts before profile edits that refer to them, then deletions against the effects reviewed in the draft. Coalesce repeated edits to the same record. A create followed by deletion in the same draft introduces no stored record. Publish settled operation results and read the combined settings snapshot using Task 2's recovery rules. Retain the existing shared-write wakeup, so committed changes become publication candidates after sync resumes.
- [ ] **Revalidate against original bases and acknowledged draft effects.** Use the existing tag deletion planner for QSO outcomes and the existing equipment preview and repair choices for profile impacts. Preview the sequence in Apply order. Carry original records through the review and use authoritative results of preceding successful writes to account for changes caused by this Apply. If needed for an overlapping deletion, expose exact post-write rows from the existing transaction's save results. Before deletion, compare a fresh preview against the approved effects and expected records, including exact membership, referrers and selected replacements. A change attributable to neither the reviewed basis nor a successful preceding operation is stale. Pass the verified fresh preview to the existing guarded delete method, which rechecks inside its write transaction. If a prerequisite failed and the resulting effect differs from what was confirmed, fail that deletion individually and require a new review. Keep selected-logbook fallback and equipment deletion with profile repairs atomic within their existing operations.
- [ ] **Verify durable outcomes.** Run `cargo +1.99.1 test -p clacks-desktop --lib --locked --offline settings_apply` and `cargo +1.99.1 test -p clacks-client-store --test integration --locked --offline settings`. Run the client-store logbook deletion filters as well. Check exact records and selected-view fallback, rather than treating a result message as proof of a database mutation.

## Task 4 — Wire the Settings screen and its sections

**Files** — The screen, section, menu, and workbench UI files in the file map, and `lib/clacks-desktop/src/ui/tests/menu_commands.rs`. Put feature-specific component checks in `ui/settings/tests.rs`.

**Interface** — Add `MenuCommand::OpenSettings` and a single `DesktopApp::open_settings(&mut self, context: &egui::Context, destination: SettingsDestination)` entry point. `SettingsDestination` identifies the default screen, a section, or a profile by its stable ID. `SettingsScreen` owns the `SettingsDraft`, entry focus, results by setting, and one Apply in flight. It uses Task 1's open intent and readiness watches, Task 3's account result, the existing `ReceiverAction::Apply { next }` and `ReceiverResponse`, and the existing appearance preference and enrollment owners.

- [ ] **Pin the normal entry points.** Update existing menu tests to exercise Open Settings through command dispatch and current lifecycle gating. Add `settings_routes_shortcuts_and_restores_workbench`. Verify the WS Suite shortcut and conflict-review profile route open the same editor, a repeated open preserves the draft, workbench write actions cannot dispatch while it is active, and closing restores focus and the unfinished contact. Include workspace opening/failure with Appearance available and no workspace edits yet.
- [ ] **Install the main-window view.** Render Settings in place of the workbench content and block workbench editing through the native menu and any auxiliary entry points while it is active. Preserve the normal Quit and shutdown path. Route all entry points through `open_settings`, including the WS Suite error shortcut and station-profile conflict repair. Replace the obsolete settings subcommands and their dynamic Connection label with the platform-specific entry documented in the design. Keep the native menu route, labels, wakeup, and platform-specific placement review in Task 5.
- [ ] **Render the six sections in the left sidebar and stage edits.** Reuse logbook policies and forms, profile/equipment field rendering and builders, WS Suite normalization and interface checks, and appearance fonts and live preview. Place the lists and editor content inside their sections. In the draft, overlay staged values by record ID for navigation, selections and confirmations. Share reusable field rendering with the workbench where it removes duplication while keeping the existing Operating settings nested save path. Confirmation dialogs stage their approved effect. Escape first dismisses an active confirmation; Settings dismissal then follows D295. A stale deletion result offers a new impact review at that record, with still-applicable choices available for reconfirmation.
- [ ] **Compose Apply and Connection lifecycles.** Validate the submitted forms individually, exclude invalid changes with their diagnostics, and run the valid account, receiver, and appearance operations through their existing owners. Only one submitted draft can be in flight. Wait for every admitted operation to settle before accepting another Apply, sign-in or Settings dismissal. Keep the application Quit path available. Clear the completed draft, keep the current section, and show authoritative values. Use the current appearance preference commit and eframe storage path. If WS Suite returns `ReceiverResponse::Applied` with failed reception, display the saved configuration and the activation error separately. Connect and Reauthorize use the existing browser flow, leave other draft edits intact, and disable Apply through sign-in and any workspace reopen. Revalidate retained edits under the new workspace identity and basis. Closing Settings during sign-in uses the existing local cancellation rules.
- [ ] **Show outcomes at the point of use.** With pending edits, show one **Apply** and **Cancel** pair. After Apply, disable Apply and show **Close** until the next edit. Show the last Apply failure icon, affected section icons, and setting-level diagnostics with accessible text. Keep the current section selected. Cancel restores the committed appearance and discards only the unapplied draft. Recovery publications update the saved basis for unedited values and keep newer raw edits and their expected record bases intact.
- [ ] **Verify the editor.** Add `settings_apply_clears_draft_and_marks_failed_items` for a valid logbook rename plus an invalid receiver port. Assert that the rename saves, the saved port is displayed, Apply is disabled with its result indicator, WS Suite navigation and the port carry diagnostics, and the current section stays selected. Exercise committed receiver intent with failed activation, Cancel after preview, cross-section navigation, confirmation without a write, and automatic refresh arriving after a new edit. Run `cargo +1.99.1 test -p clacks-desktop --lib --locked --offline ui::settings` and `cargo +1.99.1 test -p clacks-desktop --lib --locked --offline ui::tests::menu_commands`.
