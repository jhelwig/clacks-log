# Production Desktop Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native execution, or superpowers:subagent-driven-development if explicitly selected. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the production Windows desktop foundation for issue #46, using the real local store, responsive native rendering, workspace activation, graceful shutdown and production observability.

**Architecture:** A thin `bin/clacks-log` entry point calls `lib/clacks-desktop`. The desktop library composes egui/eframe/wgpu, one owner-process Tokio runtime, the existing store and standard telemetry adapters. Domain/storage behavior remains in the existing libraries; later workflows extend this application.

**Tech Stack:** Rust 1.99.1, egui/eframe 0.37.0, Tokio 1.54.1, SQLx 0.9.0/SQLite, standard-library file locks, interprocess 2.4.7, tracing/metrics and OpenTelemetry 0.33 using OpenTelemetry Protocol (OTLP) export.

**Spec:** [Desktop application foundation](../../desktop.md), with [client storage](../../client-store.md), [native values](../../native-model.md) and [observability](../../observability.md).

## Global Constraints

- Rust 1.99.1 comes from `rust-toolchain.toml`; use workspace-inherited package metadata/dependencies and the committed lockfile.
- Windows is the MVP target; retain macOS/Linux foundations. Actual native Windows acceptance is required; cross-compilation is insufficient.
- Libraries belong under `lib/<crate-name>`, thin applications under `bin/<application-name>`. No `mod.rs` outside tests, facade/glob re-exports, production panic shortcuts or unchecked indexing.
- Preserve unrelated changes in `references/desktop-toolkit.md`. Create the implementation worktree from the committed specification/plan, not by including those changes.
- No Python, xtask, disposable demonstration application, project telemetry framework or direct use of the TrustedQSL sources.
- Existing files are never silently replaced after errors. Keep one read-only store preflight, SQLx migration history, ordinary transactions and stale-save protection; add no database marker, startup migration lock, schema-version copy or custom write queue.
- One owning process per workspace; the lifetime lock coordinates the application and activation, not SQLite correctness.
- Keep all future workflow boundaries: #7/#8/#9/#10, enrollment #12 and packaging #35 remain separate.
- Use focused instrumentation, ordinary control flow and standard framework lifecycle facilities. Application boundaries own deliberate error reporting and measurements; libraries do not install global exporters.
- Every public API needs a production caller and standalone rustdoc. Use named fields, focused modules and contextual commit messages with bodies.
- Do not push, create a PR or start implementation merely because this plan exists. Use the user's authorization for each subsequent action.

## Review Focus

1. Path aliases and simultaneous launches must identify one owner without treating permission errors or an unresponsive owner as permission to create another. Pin in Task 4 process tests.
2. Failure partway through first initialization must not leave a believable initialized account missing its default definitions. Pin in Task 2 transaction tests.
3. Closing while initialization finishes must close the returned pool instead of publishing Ready or losing track of resources. Pin in Task 6 lifecycle tests.
4. Environment/file overrides must neither enable export accidentally nor disclose credentials in validation errors. Pin in Tasks 3 and 5.
5. Renderer/window failure and unavailable telemetry must not strand the lock, database connections or tracked work. Pin in Tasks 5–7.
