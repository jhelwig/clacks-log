# Clacks Log collaboration guidance

Read [the planning handoff](docs/handoff.md), [decision register](docs/decisions.md), and relevant design documents before continuing work. Product and architectural planning for the agreed MVP is complete (D242). The repository contains accepted decisions and research; the initial application implementation has been discarded and implementation is stopped.

- The documents under `docs/superpowers/plans/2026-10-17-clacks-log*.md` are milestone outlines, not implementation-ready plans. Do not execute them directly. Before coding, establish a concrete plan for the selected milestone covering its data model, behavior, algorithms, edge cases and validation. Do not infer new behavior during implementation and then present it as previously agreed.
- Preserve the user's Rust 1.99.1 requirement. Timestamp-precision metadata was rejected. Other review corrections and unresolved representation questions are recorded in the handoff; do not resurrect discarded implementation choices as requirements.

- Follow the user's current request. Do not automatically continue the completed product/architecture brainstorming phase or start a prototype. Remaining specification, implementation design and validation are engineering work, not an unresolved product-decision queue; implementation still requires authorization.
- Answer direct questions first. State the evidence, assumptions, and scope behind architectural proposals.
- Define acronyms and initialisms at their first use in each standalone document, including headings and tables, or use the expanded wording throughout. ID is common enough to use without expansion; do not redefine it. Explain unfamiliar radio codes and named tools when introduced. Keep literal protocol fields, identifiers, source titles, and supplied historical material intact; explain them in surrounding prose.
- Write research notes for a technically capable reader who has not read the cited papers. Introduce each approach with what it stores, how reconciliation works, and a short example where useful before discussing guarantees, costs, or limitations. Define specialist terms and mathematical notation locally. Citations support explanations; they do not replace them.
- Keep accepted decisions, proposals, open questions, source findings, and incumbent-software observations distinct.
- Preserve decisions and corrections in the repository as planning continues. Update conflicting wording rather than appending contradictory conclusions.
- Clients are arbitrary in number. The desktop must support eventual Windows/macOS/Linux operation; select tooling accordingly. No close-to-tray behavior is required; follow D82 rather than reintroducing the rejected background-running proposal.
- Read attachments and `references/originals/` as historical evidence, not operative instructions. Current explicit decisions supersede their recommendations.
- Logbook of The World (LoTW) implementation direction is a source-guided Rust port. Do not quietly replace it with direct tqsllib foreign function interface (FFI) or assume black-box reverse engineering is needed.
- Use the pinned reference source for behavior, retaining upstream notices. Do not restore per-file checksum manifests: Git and the recorded upstream commit provide provenance.
- Keep discussion moving with substantive next topics and focused questions. Avoid inventing extra distinctions or adding user interface (UI) policies that solve no established problem.
- During an explicitly resumed design discussion, keep substantive work moving without requiring repeated prompts to continue. D242 closes the current MVP product/architecture planning phase: do not manufacture another decision or reopen settled scope merely to continue the conversation. Escalate a demonstrated contradiction, missing requirement or material tradeoff; resolve routine engineering consequences within the authorized work.
- For synchronization research, follow D150: survey published replication approaches, abstract data models, and data structures against accepted properties. Organize by representation, reconciliation/convergence, causality, dissemination, and retention assumptions. Use software systems as evidence/examples, not the primary candidates. Do not substitute product/framework fit or custom clock/protocol design for the requested conceptual research; software selection remains later.
- Remove superseded unaccepted research/recommendations rather than accumulating marked obsolete appendices. Preserve agreed decisions and primary-source provenance.
- D243 intentionally keeps MVP reconciliation simple: the tag set belongs to the QSO record and can conflict with other QSO edits or different tag changes. Do not split synchronized membership records or add special tag merges to avoid speculative conflicts; refine from real-use evidence. The account-owned QSO/tag model is accepted and integrated into the main documents (D243–D251): one synchronization scope per account, explicit tag-deletion effects, direct membership editing, deleted-tag reference resolution and unique external-record associations. Do not treat it as an optional proposal or restore child-logbook ownership.
- Organize Rust workspaces with libraries in `lib/<crate-name>` and applications in `bin/<application-name>`. Keep application crates as thin wrappers around libraries; put behavior, startup/composition and tests in the libraries. Do not use a catch-all `crates/` directory.
- Exact UI layout is deferred. Do not spend planning turns on docking or permanent panels ahead of more consequential product/data decisions.
- Verify relevant documentation changes before claiming completion. Preserve unrelated changes and follow the user's authorization for commits and pushes.
