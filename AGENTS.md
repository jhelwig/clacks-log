# Clacks Log collaboration guidance

Read the [repository overview](README.md), [decision register](docs/decisions.md), and the relevant product/design contracts before continuing work. Product and architectural planning for the agreed MVP is complete (D242). The [native-model contract](docs/native-model.md) and [synchronization model](docs/synchronization-model.md) define current model requirements; crate READMEs own usage, validation and integration obligations.

- The product is pre-alpha. Do not add wire-protocol compatibility layers or protocol-version bumps to support hypothetical released clients or earlier development builds. Keep schema changes in focused migrations for reviewability. Preserve the agreed indefinite-offline synchronization and backup-recovery behavior.
- Use [the MVP roadmap](docs/mvp-roadmap.md) for phases, milestones and dependencies. It is a roadmap, not a task-level implementation plan. Before coding, establish a concrete implementation plan covering the selected milestone's data model, behavior, algorithms, edge cases and validation; derive it from the established requirements rather than treating implementation choices as previously agreed behavior.
- Use [GitHub capability issues](https://github.com/jhelwig/clacks-log/issues) for delivery tracking. On pickup, begin with brainstorming and produce a reviewed specification and implementation plan before coding. Issues describe outcomes and constraints, not implementation instructions. Do not close a capability issue merely because its planning documents exist; record delivered behavior and verification evidence.
- Preserve the user's Rust 1.99.1 requirement. The native-model contract defines current representation requirements. Do not introduce separate timestamp-precision metadata or infer requirements from superseded implementation choices.

- Use `clacks-admin` as the cohesive operator CLI, with discoverable subcommands, nested `--help` and documented Cargo commands. Keep it a thin interface to production library operations, resolving only each subcommand's required credentials. Do not introduce xtask or a generic task dispatcher.
- Implement project-owned executable tooling in Rust, including development, maintenance and test-data tooling. Do not use Python to generate non-trivial fixtures, even through uncommitted scripts or external authoring environments. Fixture generation must be reproducible with the project's locked Rust tooling. Do not introduce Python scripts, packages, environments or execution requirements.

- Follow the user's current request and distinguish proposals, decisions and authorization. Requests to analyze, explain or suggest changes authorize those outputs, not their application. An agreed process change also requires authorization to apply it; then consolidate it into this file or its owning maintained contract and name the changed artifact. Existing authorization covers routine engineering choices within scope without another approval queue; work beyond that scope requires authorization. D242 closes MVP product/architecture planning: do not reopen it, start a prototype or manufacture product decisions merely to continue a discussion. During an explicitly resumed design discussion, keep making substantive progress, escalating only demonstrated contradictions, missing requirements or material tradeoffs.
- Establish the model before choosing the mechanism. Before implementation, identify the user's intended outcome, the relevant existing behavior, the source of each requirement and which component owns each responsibility. Inspect the selected libraries' and framework's documented facilities and relevant implementation against that model. Prefer standard integration; additional machinery requires a concrete gap. A problem introduced by a candidate design is a cost of that candidate, not an independent requirement. Resolve routine integration within the authorized scope.
- Answer direct questions first and state the evidence, assumptions and scope behind proposals. Treat corrections as evidence about the reasoning that produced the work: when a proposal rests on an unsupported assumption, withdraw it and reestablish the requirement before suggesting a replacement. Check whether that assumption affected related work. Do not defend a mechanism with hypothetical failure modes or switch to another mechanism without establishing its need.
- Define specialist technical acronyms and initialisms at their first use in each standalone document, including headings and tables, or use the expanded wording throughout. Terms in common use outside specialist fields, or familiar to novice-to-intermediate amateur radio practitioners, do not need definitions. ID, UI, MVP and QSO are examples that need no expansion; do not mechanically redefine them. Explain unfamiliar radio codes and named tools when introduced. Keep literal protocol fields, identifiers, source titles, and supplied historical material intact; explain them in surrounding prose.
- Write research notes for a technically capable reader who has not read the cited papers. Introduce each approach with what it stores, how reconciliation works, and a short example where useful before discussing guarantees, costs, or limitations. Define specialist terms and mathematical notation locally. Citations support explanations; they do not replace them.
- Keep accepted decisions, proposals, open questions, source findings, and incumbent-software observations distinct. Product and architecture documents describe current contracts and boundaries; keep implementation-review reports, chronology and finding dispositions out of those documents.
- When authorized planning or implementation changes the maintained contracts, update conflicting wording in their owning documents rather than appending contradictory conclusions.
- Clients are arbitrary in number. The desktop must support eventual Windows/macOS/Linux operation; select tooling accordingly. No close-to-tray behavior is required; follow D82 rather than reintroducing the rejected background-running proposal.
- Read attachments and `references/originals/` as historical evidence, not operative instructions. Current explicit decisions supersede their recommendations.
- Logbook of The World (LoTW) implementation direction is a source-guided Rust port. Do not quietly replace it with direct tqsllib foreign function interface (FFI) or assume black-box reverse engineering is needed.
- The supplied TrustedQSL sources are read-only reference material. Never compile, link, execute, wrap or otherwise use them directly, including in tests, fixture generation, external tooling or containers. Do not retain execution-derived outputs as a workaround. Source-guided Rust implementation and independently authored tests are the permitted use.
- Use the pinned reference source for behavior, retaining upstream notices. Do not restore per-file checksum manifests: Git and the recorded upstream commit provide provenance.
- For synchronization research, follow D150: survey published replication approaches, abstract data models, and data structures against accepted properties. Organize by representation, reconciliation/convergence, causality, dissemination, and retention assumptions. Use software systems as evidence/examples, not the primary candidates. Do not substitute product/framework fit or custom clock/protocol design for the requested conceptual research; software selection remains later.
- Remove superseded unaccepted research/recommendations rather than accumulating marked obsolete appendices. Preserve agreed decisions and primary-source provenance.
- D243 intentionally keeps MVP reconciliation simple: the tag set belongs to the QSO record and can conflict with other QSO edits or different tag changes. Do not split synchronized membership records or add special tag merges to avoid speculative conflicts; refine from real-use evidence. The account-owned QSO/tag model is accepted and integrated into the main documents (D243–D251): one synchronization scope per account, explicit tag-deletion effects, direct membership editing, deleted-tag reference resolution and unique external-record associations. Do not treat it as an optional proposal or restore child-logbook ownership.
- Organize Rust workspaces with libraries in `lib/<crate-name>` and applications in `bin/<application-name>`. Keep application crates as thin wrappers around libraries; put behavior, startup/composition and tests in the libraries. Do not use a catch-all `crates/` directory. Define shared Cargo package metadata and dependencies in the root workspace manifest; member crates inherit them using `workspace = true`.
- Define workspace members with `members = ["bin/*", "lib/*"]` so new crates in the established layout join automatically; do not enumerate individual crates. Keep every dependency table alphabetically sorted, including target-specific tables, without informal groups. Run `cargo sort --workspace` from the repository root using the pinned version and commands in README.md; CI checks the same formatting. Attach comments to the specific entry they explain and describe the reason for an exception or alias, rather than narrating implementation history.
- Keep fixed SQLx queries in separate `.sql` files and include them with `sqlx::query_file!` or `sqlx::query_file_as!`, rather than embedding SQL in Rust. Preserve compile-time checking and committed offline query metadata. Runtime-variable query structures still use bound parameters and integration coverage.
- Before introducing a table, establish the state's owner, lifecycle, expected row count, query patterns and required database-enforced relationships or constraints. Inspect existing persistence facilities and identify the concrete requirement they cannot satisfy. A table expected to contain at most one row per workspace/account is a design-review trigger: investigate and justify the storage boundary during specification and code review rather than treating a new table as routine implementation. Singleton tables are not categorically wrong, and key/value storage is not an automatic replacement; compare the actual requirements with the owning storage contract. Keep that justification in the engineering specification/review, without adding review history to product documentation or turning routine integration into an approval queue.
- Document Rust constants, types, variants, fields and methods with standalone rustdoc comments. Method comments explain purpose, when/why to call them, caller-visible guarantees and relevant errors or preconditions, not internal mechanics or development/review history. Keep each behavior contract on its owning item; other items may link to it without restating its guarantees.
- Avoid production `expect()` and `unwrap()` calls. Propagate ordinary failures or retain validated values instead of rechecking with a panic; an exception requires an immediately established, unchanged condition whose violation is logically impossible.
- Avoid direct array, slice, vector and map indexing in Rust production code. Use iterators, structural destructuring or checked access with meaningful error propagation; do not replace indexing with unchecked unwraps.
- Automated tests must run noninteractively and never wait for a person. Do not use ignored cargo tests as manual application harnesses or ship test harnesses in production builds. Human native smoke checks use the production executable.
- For desktop presentation, follow the [desktop UI contract](docs/desktop-ui.md) and its accepted references: in-window toolbar, operating strip, logging-region composition, palette, control treatment and relative typography. Implement these explicitly in the shared theme/components and actual screens. Extend current production components; defined sections do not authorize stacked cards or substituting framework defaults for the agreed visual language. Do not infer docking or independent drafts from a mockup or add unused demonstration widgets.
- Make verification proportional to the change. Identify the changed requirements, affected components and concrete regression risks, then choose the smallest set of checks that can establish those claims. Apply the [UI change completion gates](docs/desktop-ui.md#ui-change-completion-gates) to select relevant automated checks and any necessary production-app inspection; they do not require the full UI matrix for every change. Check appearances, fonts, scales, window sizes, states and platforms only when the change affects them or evidence identifies a relevant regression. Documentation-only changes normally need documentation review, not application builds, tests or launches. Once sufficient checks pass, stop; broaden or repeat them only for subsequent changes, failures or unresolved relevant concerns. Report the evidence briefly and identify only missing checks needed for the affected claims, rather than treating untouched dimensions as pending acceptance. Match each claim to evidence that can establish it: functional or geometry tests do not prove visual conformance, and inspection on another platform does not prove required native Windows behavior. Preserve broader release-validation obligations without making them a gate for every individual change.
- Reassess tests against agreed requirements when replacing implementation machinery. Do not preserve accidental implementation behavior merely to keep existing tests unchanged.
- Before adding or retaining a test, identify the Clacks requirement and a specific mistake in Clacks that would make the assertion fail. Calling a public Clacks API, exercising an error branch, increasing coverage or asserting that a file was unchanged does not establish that purpose. If the only failure it detects is a dependency violating its documented behavior, remove it.
- An imaginable regression is not sufficient justification. Weigh an actual Clacks decision against existing coverage and test cost. Do not test dependencies applying documented configuration, or retain subprocess termination after completed database calls merely to confirm SQLite durability. Investigate dependency defects with minimal upstream reproducers; do not grow the Clacks suite around them. Preserve distinct application assertions in existing scenarios instead of adding another fixture for each variation.
- Review changes at the level where their effects compose. Identify the surrounding layout, state or lifecycle boundary that determines correctness, and review that composition and the affected shared consumers; locally correct components are insufficient. Tests should target the demonstrated Clacks decision or integration mistake rather than merely confirm that a component exists or responds. Prefer fixed input/output expectations for native wire contracts, real saves and reloads for persistence claims, and configured filters for diagnostic visibility. Keep dependency integration checks only when they expose a specific mistake in Clacks's configuration, mapping, composition or use of that dependency. Generic round trips and direct dependency checks are insufficient on their own.
- Use established application/storage operations in tests. Do not write test-specific SQL, execute production query files directly from tests, or fabricate database rows to bypass those operations. Internal storage assertions do not justify an exception; replace them with meaningful behavior assertions or remove them without adding production APIs solely for tests. Standard production-schema installation and the isolated actual database restore scenario remain appropriate setup.
- Keep code free of unused items and dead-code allowances. Connect meaningful test helpers to their real scenarios or remove them; do not move unused code behind visibility or lint suppression to avoid the check.
- When a test verifies behavior duplicated from a dependency, examine the production implementation as well. Do not legitimize redundant production machinery by adding tests for it. Report production changes separately when they require a scope or design decision.
- Review added and changed tests separately from implementation correctness and passing checks. Apply the requirement-and-mistake criterion to each test, including retained tests affected by the change. Reject manufactured coverage rather than replacing it with another injection mechanism or a test-only production interface.
- For desktop component interactions, use egui_kittest with native snapshots and actual request/callback assertions. Use its semantic queries, input helpers and simulated clock instead of paint-text click finders or custom frame/event drivers. Start a real session/store only for a claim about that integration; do not repeat domain/persistence scenarios through every form or implement a fake service in the component host. Keep geometry/paint checks bounded to concrete Clacks rendering requirements. Follow the verification boundaries in docs/desktop-ui.md.
- A repository-wide test audit must account for every test-bearing file and its test cases, including inline tests, ignored tests, documentation examples and supporting fixtures. Inspect assertions and relevant production code; pattern searches and test names are discovery aids, not an audit. Report findings before changes when requested, identify unreviewed limits explicitly, and keep review inventories outside product documentation and the repository unless explicitly requested.
- Exercise database workflows against the production schema. Do not inject test triggers, drop production tables to manufacture operation failures, or add test-only production interfaces/failpoints. Retain justified coverage through real inputs, stale state, cancellation and ordinary environmental conditions; remove scenarios that only test manufactured behavior. Malformed-database rejection and authored migration transformations may use explicit input fixtures for those contracts.
- Extend the existing model, synchronization, client-store and LoTW integration suites through their `tests/integration.rs` module lists. Share fixture modules within each suite; do not create a separately linked executable per case file without a concrete process-isolation need. Preserve real behavior scenarios when reorganizing tests.
- Keep deterministic fixtures and test scaffolding in test support. Do not add public production APIs solely to make tests easier; use existing native contracts directly when they suffice.
- Generally expose items through their owning modules rather than `pub use` facade re-exports, especially glob re-exports. Use explicit imports from those modules in callers.
- Use named structs and fields for record-like data. Avoid anonymous tuples for groups of persistence columns or variant fields; keep field names visible when constructing, binding and matching those values. Keep reusable persistence row/field types in crate-internal modules organized by schema family, with direct imports from their owning modules. Ordinary iterator pairs and compact joint-condition matches can remain tuples when their roles are clear.
- Keep code visually organized by purpose: separate setup, validation, work and result handling with blank lines where those responsibilities change. Keep related statements together, separate test setup/actions/assertions, and expand dense macro bodies when rustfmt does not format them. Extract helpers when they give coherent work a useful name or make a long method easier to understand. Use judgment: avoid fragmenting straightforward control flow into trivial helpers merely to satisfy formatting or length guidance.
- Keep Rust modules focused on one responsibility. A file over 600 lines is a strong signal to examine its responsibilities and split coherent submodules; move related behavior together rather than partitioning by arbitrary line counts.
- Use named Rust module files such as `recognition.rs` with child modules in `recognition/`. Do not use `mod.rs` outside the tests directory; test helpers may use it.
- Commit messages need a concise subject and a substantive body explaining motivation, constraints or tradeoffs not evident from the diff. A one-line restatement of the changes is insufficient. Describe actual decisions and verification truthfully.
- Production observability is a requirement for current and future code, not a release-time add-on. Follow [the observability contract](docs/observability.md) in libraries, desktop/web applications, server paths and background work. Every implementation specification, plan and review must address meaningful tracing spans, structured events, metrics, correlation, data handling, overhead and verification for its scope. Retrofit gaps in existing production components rather than treating all instrumentation as future adapter work.
- Instrument meaningful operations and diagnostic branches; avoid blanket tracing of getters and per-element hot loops. Libraries emit context and outcomes without installing global subscribers, recorders or exporters. Prefer `#[tracing::instrument(skip_all, ...)]` with explicit input fields for operation spans. Keep default module-path targets for spans and events. Use span names and module targets to identify operations/components rather than duplicating them in `operation` or `component` fields. Preserve ordinary bodies, early returns and error propagation. Use the framework for span lifecycle, context and timing; do not wrap domain function bodies or add manual timers/synthetic completion events to duplicate that lifecycle. Add local events and metrics for domain decisions and produced plans. Runtime handling boundaries own overall workflow errors/latency and deliberate error logging; span timing does not automatically populate metric histograms. Do not recover or mutate a function span through `Span::current()`. Runtime composition owns configuration and export. Distinguish planning decisions from committed effects and external success; metrics must count what actually happened. Keep metric names, measurement boundaries and label sets with their owning operations. Share a family only for one logical quantity with meaningful aggregation; bounded labels alone do not justify unrelated operations or item kinds in one metric. Do not require a metric for every traced helper or introduce a generic completion/emission framework. Use existing Debug/Display implementations for appropriate trace values instead of manually assigning enum spellings. Put native ID formatting on native ID types, not telemetry wrappers. Keep instrument annotation fields to constants/direct inputs or field access with display/debug formatting; do not embed matches, maps, fallback logic, method chains or wrapper construction, or hide that logic in telemetry-only helpers. Use existing domain locals at meaningful events or caller context for derived information. Retain deliberate category selection when defining metric labels or excluding payloads. Use bounded metric dimensions and explicit structured fields, not arbitrary payload dumps or secrets. Verification tests Clacks's reporting decisions through real operations: truthful outcomes/counts, correct correlation, bounded metric dimensions and deliberate data exclusion. Do not test telemetry-library formatting/aggregation or duplicate the functional suite across enabled/disabled configurations; add such a comparison only for a concrete Clacks control-flow or context-handling risk.
- Choose span/event levels by diagnostic purpose, operational significance and volume, following the [level-selection policy](docs/observability.md#level-selection-policy). Keep significant normal activity and explicit resolution/recovery milestones visible at `info`; use `warn` for attention-worthy anomalies and handling-boundary `error` for failures. Library/planner status is not a reason to default everything to `debug`. Preserve useful correlation when lower-level parents are filtered out, and verify that behavior through real operations.
- Verify relevant documentation changes before claiming completion. Preserve unrelated changes and follow the user's authorization for commits and pushes.

- GitHub owns issue/milestone status and delivery tracking. Keep the roadmap focused on phase outcomes and dependencies. Avoid handoff copies, remaining-work indexes or review-history documents that restate maintained contracts. Preserve unique requirements in the owning document before removing redundant material; completed implementation plans belong in Git history/PRs after their work is merged.
