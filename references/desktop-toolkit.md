# Desktop toolkit comparison and selected direction

17 October 2026. **D215 selects egui. Capability findings and unaccepted implementation details remain distinguished below; this is not an implementation plan.** The user keeps Tauri in the comparison but prefers no TypeScript and as much native Rust as practical. The selection follows that preference and the completed Clacks-specific comparison. PostgreSQL for the server and embedded SQLite for the client are already selected in D213. No application, visual mockup, toolkit installation, performance benchmark or accessibility test was created or run for this report.

## Selected direction (D215)

Use **egui through eframe, with egui_extras for contact tables**, keeping the application, interface behavior and domain operations in Rust. SQLite and the ordinary transaction approach remain unchanged. D215 accepts the toolkit direction. Exact versions, renderer, optional components and layout remain open; no implementation plan or prototype is approved.

GTK still supplies more integrated table selection, keyboard and widget behavior. Clacks needs contact lists, forms, indicators and explicit resolution choices; it has no accepted requirement for a spreadsheet engine, custom canvas or comprehensive inline table editor. That limits the benefit of choosing the largest widget stack.

**egui's required application work is bounded and concrete:** adapt indexed SQLite query results to a virtualized table, retain selection by stable contact ID, connect header/filter controls to ordering/query state, and compose standard text/choice controls for entry and resolution. TableBuilder supplies scrolling headers/columns and cell composition; TableBody supplies visible-row rendering. There is no recommendation to implement text editing, layout, scrolling or a generic data-grid engine from scratch. Full range-selection/navigation behavior needs deliberate composition or a qualified reusable component, but it is not a reason to invent broader spreadsheet requirements. [Table primitives](https://docs.rs/egui_extras/latest/egui_extras/struct.TableBuilder.html), [visible rows](https://docs.rs/egui_extras/latest/egui_extras/struct.TableBody.html)

Iced remains a Rust-authored alternative with asynchronous input, but the reviewed
table and unfinished upstream accessibility integration leave additional
presentation integration work.

The choice accepts egui's custom-rendered controls, explicit stable widget identity and more application-level table interaction state in return for avoiding GTK's object/binding/deployment stack and TypeScript. It is not a claim of measured productivity, native operating-system widgets, perfect accessibility or superior rendering speed. Existing text controls, AccessKit integration and repaint scheduling remain useful building blocks; custom table semantics and actual keyboard/input behavior still need verification.

The constraints remain no TypeScript preferred, native Rust where practical, and no GNU General Public License (GPL) distribution route. Slint is not selected for Clacks. Tauri with a Rust frontend and Dioxus were considered as webview alternatives, but do not improve this combination of integrated table behavior and avoiding a browser dependency. Qt remains a technically strong desktop option with more C++/Rust integration. No blanket prohibition of LGPL dependencies or requirement for an all-Rust dependency tree has been stated.

## Agreed requirements and assessment criteria

A radio contact is called a QSO. A user interface is abbreviated UI. Minimum viable product is abbreviated MVP. WS Suite means the WSJT-X family of weak-signal radio applications; it supplies local User Datagram Protocol (UDP) updates. Amateur Data Interchange Format (ADIF) is the contact import/export format. A webview is an embedded browser rendering surface, not necessarily a remotely hosted website. Virtualization means rendering the visible rows rather than constructing a widget for every stored record; it does not mean selective synchronization.

### Contact tables and selected operations: the differentiator

GTK documents visible-item cell factories, configurable column sorting/resizing and selection integrated with the model. MultiSelection includes select-all and range operations. Its list framework explicitly distinguishes item identity from position; Clacks must preserve contact identity when rows move. These are existing facilities, not a proposal to write a custom data grid. [ColumnView](https://docs.gtk.org/gtk4/class.ColumnView.html), [MultiSelection](https://docs.gtk.org/gtk4/class.MultiSelection.html), [list models](https://docs.gtk.org/gtk4/section-list-widget.html)

GTK does not automatically page SQLite. A view model adapts local query results; use a supplied list store when sufficient or the normal model interface if loading needs to be incremental. Do not infer that rendering only visible rows bounds the memory used by an eagerly loaded dataset. A selected/filtered operation must cover its actual intended scope, not only visible rows. Those obligations apply to every candidate.

egui_extras supplies fixed headers, resizable columns and arbitrary widgets per cell. TableBody::rows and heterogeneous_rows render only visible rows. TableRow::set_selected sets highlighting; Response reports interaction. They are useful building blocks, but do not alone implement identity-based multi-selection and keyboard navigation. No unsupported claim of poor table rendering performance is needed. [Table builder](https://docs.rs/egui_extras/latest/egui_extras/struct.TableBuilder.html), [visible rows](https://docs.rs/egui_extras/latest/egui_extras/struct.TableBody.html), [selection highlighting](https://docs.rs/egui_extras/latest/egui_extras/struct.TableRow.html)

Community components are part of the comparison: egui-table-kit advertises filtering/sorting and multi-row selection; egui_tabular documents keyboard movement. These can reduce custom work. Their existence does not establish the chosen version's accessible table semantics, stable selection under incoming changes, or compatibility with the eventual egui release. They are candidates to verify, not a reason to insist Clacks must build everything itself. [egui-table-kit](https://github.com/xangelix/egui-table-kit), [egui_tabular](https://github.com/romixlab/egui_tabular)

Iced 0.14's built-in Table is documented, but its constructor iterates the supplied rows and creates every cell. Its public interface covers layout rather than a table selection/sorting controller. Wrapping it in a scroller does not remove that construction cost. This is a finding about the examined implementation, not every possible Iced table. [Published table](https://docs.rs/iced/0.14.0/iced/widget/table/struct.Table.html), [released source](https://raw.githubusercontent.com/iced-rs/iced/0.14.0/widget/src/table.rs)

The separate iced_table 0.14 crate supports Iced 0.14 dependencies, resizing and coordinated header/body scrolling. It explicitly delegates some scroll/resize updates to the consumer. It is a real reusable option, not evidence that Iced lacks tables. The reviewed interface does not establish a complete virtualized, accessible, identity-aware selectable contact grid. GTK's integrated path remains less fragmented for this workflow. [Extension source and dependencies](https://docs.rs/iced_table/latest/src/iced_table/lib.rs.html)

### Forms, time fields and asynchronous changes: feasible in all three

GTK Entry exposes ordinary editing, with Editable controlling whether the user can change a field. egui TextEdit and Iced TextInput supply text-input controls, so none requires building an editor just to enter callsigns or timestamps. The two lock states, supplied timestamps and reset after save are Clacks application logic. This workflow does not justify a winner by itself. [GTK text input](https://docs.gtk.org/gtk4/class.Entry.html), [editable flag](https://docs.gtk.org/gtk4/method.Editable.set_editable.html), [egui text editing](https://docs.rs/egui/latest/egui/widgets/text_edit/struct.TextEdit.html), [Iced text input](https://docs.rs/iced/0.14.0/iced/widget/text_input/struct.TextInput.html)

GTK's standard keyboard navigation and shortcut mechanisms reduce baseline form plumbing. It explicitly documents that primary shortcuts do not automatically map to Command on macOS; cross-platform behavior still needs configuration. Iced supplies focus-next operations, and egui stores focus/interaction state. Neither is dismissed as incapable of keyboard use. [GTK input handling](https://docs.gtk.org/gtk4/input-handling.html), [Iced focus operation](https://docs.rs/iced/0.14.0/iced/widget/operation/fn.focus_next.html), [egui interaction memory](https://docs.rs/egui/latest/egui/struct.Memory.html)

For UDP input, directory results and synchronization, GTK's main-loop integration, egui repaint requests and Iced subscriptions are adequate normal mechanisms. egui explicitly supports delayed repaint for a clock displaying seconds; continuous animation is unnecessary. Iced subscriptions are designed for external event streams and timer ticks. GTK documents keeping blocking work off its main loop. No new message broker, custom write queue or graphics loop is required by this comparison. [GTK event loop](https://gtk-rs.org/gtk4-rs/stable/latest/book/main_event_loop.html), [egui repaint scheduling](https://docs.rs/egui/latest/egui/struct.Context.html#method.request_repaint_after), [Iced subscriptions](https://docs.rs/iced/0.14.0/iced/struct.Subscription.html)

Conflict review is structured form composition in all three: show differing values, record per-field choices and apply existing reconciliation rules. No renderer provides those rules. GTK has a feature-coverage advantage in the surrounding table/navigation facilities; D215 selects egui for Clacks.

### Accessibility, licensing and deployment: weigh the costs explicitly

GTK's column view exposes table roles, and the AccessKit backend introduced for Windows/macOS supplies platform integration in appropriate GTK builds. egui also exposes built-in widgets through AccessKit; custom-painted or visual-only content needs explicit semantic information. Neither bridge guarantees that Clacks's custom review controls or a third-party grid are accessible. [GTK platform bridge](https://blog.gtk.org/2025/02/01/whats-new-in-gtk-winter-2025-edition/), [egui semantic support/testing](https://github.com/emilk/egui/blob/main/docs/accessibility.md)

Iced's upstream accessibility implementation issue remains open, and the inspected AccessKit integration is a draft describing only partial widget support. A fork may supply more, but adopting/maintaining one is not assumed. That is a current integration risk; accessibility remains a quality criterion rather than a newly imposed certification target. [Implementation tracking](https://github.com/iced-rs/iced/issues/552), [draft implementation](https://github.com/iced-rs/iced/pull/3111)

GTK's published licensing permits proprietary applications without license fees or royalties, subject to the LGPL obligations. gtk4-rs itself uses MIT. This differs from requiring GPL distribution of Clacks or a promotional About widget. It does not mean LGPL has no obligations; chosen library builds and their dependency licenses need a release inventory. egui and Iced offer MIT licensing and simpler runtime-license obligations. No permissive-only dependency policy has been inferred. [GTK licensing statement](https://github.com/GNOME/gtk/blob/main/README.md), [GTK terms](https://github.com/GNOME/gtk/blob/main/COPYING), [gtk4-rs license](https://github.com/gtk-rs/gtk4-rs/blob/main/LICENSE), [egui MIT](https://github.com/emilk/egui/blob/main/LICENSE-MIT), [Iced MIT](https://github.com/iced-rs/iced/blob/0.14.0/LICENSE)

Windows GTK applications normally bundle GTK and its runtime dependencies; users should not need a development toolchain or manual GTK installation. Building and maintaining that bundle is one GTK cost. The macOS port also needs application bundling and platform conventions; not every control becomes a native system widget. egui/eframe and Iced avoid that GTK runtime bundle, although platform/graphics dependencies and installers still exist. No comparative installer size, startup time or memory figure was measured. [GTK Windows distribution](https://www.gtk.org/docs/installations/windows), [macOS integration](https://docs.gtk.org/gtk4/osx.html)

### Result and remaining verification

Choose egui/eframe because it meets the documented Clacks presentation needs while keeping interface development in Rust. Use egui_extras table primitives and ordinary application state rather than assume a general custom grid is necessary. GTK has stronger integrated selection/navigation facilities, but that is only one part of total development effort. Iced's event model is attractive, but its reviewed table/accessibility path provides no compensating advantage here.

The capability comparison establishes a recommendation; actual productivity and interaction quality remain empirical. Verify representative logbook size, form focus under incoming updates, table keyboard/selection semantics, assistive technology and a packaged Windows build when a design/prototype is authorized. No prototype has been run, so do not claim that egui will necessarily be easier in practice. D215 selects egui; exact compatible versions, optional table extensions and interface layout remain unselected.

## Primary-source findings

### Tauri: native application core, locally packaged web presentation

Tauri uses a Rust core with operating-system webviews: WebView2 on Windows, WKWebView on macOS and WebKitGTK on Linux. The core owns application state while the webview renders the presentation. This is a multi-process desktop application, not an independently deployed client backend service. [Process model](https://tauri.app/concept/process-model/)

Tauri supplies commands from presentation to Rust and events/channels in the other direction. Ordinary toolkit communication is sufficient; no custom message broker or database write queue is proposed. [Calling Rust](https://tauri.app/develop/calling-rust/), [calling the presentation](https://tauri.app/develop/calling-frontend/)

Its web ecosystem advantage has concrete examples: React Aria documents accessible table selection, keyboard and sorting behavior; TanStack Table supplies headless table logic, with virtualization composed separately. Headless means the library supplies behavior/state rather than finished visual controls. Tauri itself supplies neither package. Selecting a headless table alone would still leave Clacks responsible for keyboard/accessibility/rendering integration. [React Aria Table](https://react-aria.adobe.com/Table), [TanStack Table](https://tanstack.com/table/latest), [virtualization guide](https://tanstack.com/table/latest/docs/framework/react/guide/virtualization)

The Windows installer supports handling the WebView2 dependency, including an offline installer option. Runtime offline use is distinct from offline installation; existing offline-operation decisions do not automatically require a completely offline installer. Prefer a maintained runtime strategy over pinning a browser forever. Linux webview/library packaging and macOS signing remain platform work, not benefits that disappear because the interface is web-based. [Windows distribution](https://tauri.app/distribute/windows-installer/)

Application tests must include the actual embedded renderer. Tauri documents WebDriver support on Windows/Linux, with a paid third-party route for macOS; do not assume ordinary browser tests alone cover every packaged desktop path. [Desktop automation](https://tauri.app/develop/tests/webdriver/)

### Rust-authored web interfaces: Dioxus and Tauri with Leptos

A webview does not require TypeScript application code. Dioxus desktop runs Rust application/view code with its documented platform-webview backend, and its 0.7 component offering includes keyboard/accessibility primitives. Tauri also documents integration with Leptos, a Rust web framework. These are relevant alternatives under the Rust preference, not desktop widget toolkits. [Dioxus desktop](https://dioxuslabs.com/learn/0.7/guides/platforms/desktop/), [component offering](https://dioxuslabs.com/blog/release-070/), [Leptos integration](https://v2.tauri.app/start/frontend/leptos/)

The tradeoff is component integration: a Rust frontend does not automatically make React-oriented table/form packages directly reusable. It could reduce language duplication, but building or adapting the necessary rich table behavior could outweigh that benefit. This report establishes credible primitives, not an equivalent complete Clacks grid in every ecosystem. Under the clarified preference, prioritize Rust-native candidates rather than accepting TypeScript for that component-access advantage. A demonstrated suitable Rust web grid/form composition could make a Rust-authored webview approach more attractive without changing the Rust core or SQLite decision.

### Qt: distinguish Widgets, Quick and bridge maturity

Qt's model/view architecture separates data, view, selection and editing delegates. This is a close fit for local contact tables without allocating a separate stored contact object for every visible control. Widgets and Quick are distinct UI families: Widgets targets conventional mouse/keyboard desktop controls; Quick supports declarative rendered scenes. [Model/view programming](https://doc.qt.io/qt-6/model-view-programming.html), [UI families](https://doc.qt.io/qt-6/topics-ui.html)

Quick's TableView reuses delegates outside the visible area and provides table navigation/selection/editing facilities. Qt also exposes platform accessibility infrastructure. Those are meaningful capabilities, not proof of correctness for a custom contact comparison editor. [Quick TableView](https://doc.qt.io/qt-6/qml-qtquick-tableview.html), [accessibility](https://doc.qt.io/qt-6/accessible.html)

CXX-Qt creates Rust/C++ bindings and QObject subclasses usable from Qt's declarative language or C++. Its repository explicitly distinguishes limited Widgets integration from providing Widgets bindings, and describes ongoing interface development. Qt maturity therefore does not establish the maturity/completeness of every Rust integration. The older comparison table's maintenance dates are not used to rule out other bindings. [CXX-Qt scope](https://github.com/KDAB/cxx-qt)

Qt Group's own Rust bridge is currently beta/early technology, not an omitted established equivalent. It could become important, but the proposal should not depend on future maturity. [Qt Bridges status](https://www.qt.io/development/qt-framework/qt-bridges)

### Slint: a substantive non-web alternative

Slint supplies Rust integration and a declarative UI language. StandardTableView documents columns, row models, sorting callbacks, current-row changes and pointer handling. That supports a real contact-table starting point. It does not by itself demonstrate the exact multi-selection, mixed cell indicators and keyboard comparison behavior Clacks needs; inspect those compositions before relying on them. [StandardTableView](https://docs.slint.dev/latest/docs/slint/reference/std-widgets/views/standardtableview/), [desktop platforms/integrations](https://slint.dev/faqs)

Accessibility integration uses AccessKit, which bridges rendered widgets to platform assistive technology. Custom components still need roles, names and actions. [Integration announcement](https://www.slint.dev/blog/slint-1.1-released), [current accessibility guidance](https://docs.slint.dev/latest/docs/slint/guide/development/best-practices/)

An important current qualification: starting with 1.16, Fluent is the default visual style across platforms, with other built-in styles planned for deprecation. Slint explicitly separates that visual consolidation from retaining platform input behavior. Do not recommend it on the outdated premise of an indefinitely maintained native-looking theme for every platform. [Style direction](https://slint.dev/blog/default-native-style-change)

## Other approaches screened

Electron also provides a web interface, with Chromium and Node.js as central framework dependencies. It is credible if controlling the browser engine outweighs that runtime choice, but does not provide a better direct Rust-core fit than Tauri. No measured memory comparison is claimed. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model)

Flutter supports Windows/macOS/Linux desktop applications. Avalonia offers a cross-platform rendered .NET interface. They are credible alternatives if Dart or .NET becomes the preferred presentation ecosystem. They add another runtime/language and integration path without an established advantage over the finalists for the current Rust-oriented plan. This is a screening judgment, not a full component/license audit or a claim they cannot interoperate with Rust. [Flutter desktop](https://docs.flutter.dev/platform-integration/desktop), [Avalonia architecture](https://docs.avaloniaui.net/docs/fundamentals/cross-platform-architecture)

Platform-specific Windows interfaces would need another presentation implementation later. They do not meet the agreed cross-platform tooling direction as the sole architecture. This survey is representative rather than an enumeration of every Rust framework; no winner is inferred merely from omission of another project.

## Common Rust-native application boundary

Keep one ordinary desktop application with Rust domain, storage and network modules, connected to view components through the selected toolkit's normal mechanisms. Do not introduce an external client database, local server, custom UI event log or custom database write queue. Use ordinary database-library transaction management and standard asynchronous/background work mechanisms.

Keep network/database work from blocking the interface. Bind indexed SQLite query results to stable contact IDs; visible display ranges do not limit the contacts held locally or the scope of selected/filtered operations. Preserve D156 durable state/checkpoint installation before sync acknowledgment, and keep unsaved manual form state transient under D113.

Keep credentials in protected operating-system storage. Shared Rust validation and contact semantics remain authoritative; presentation updates must not turn recognition-only changes into record edits. Browser enrollment and service setup continue to open the intended system browser/web interface. The server administration interface does not impose a desktop presentation language.

## What must be verified before implementation commitment

This report recommends a direction without claiming a toolkit prototype exists. After toolkit/design approval, use a concrete mockup for review before implementing the corresponding visual flow. A subsequent bounded feasibility exercise should test the risky integrations, not build an entire logger or duplicate the finished application:
